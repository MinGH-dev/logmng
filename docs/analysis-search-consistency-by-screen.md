# 화면/기능별 검색 기능 통일 분석

각 화면·기능의 성격에 따라 **필요한 검색 축**을 정리하고, 동일 성격 화면에서 **검색 방법을 통일**하기 위한 분석 문서입니다. (코드 수정 없음, 분석만 수행)

---

## 1. 화면·기능 목록 및 도메인 분류


| 화면 ID                       | 메뉴 라벨    | 도메인        | 목록/검색 성격                     |
| --------------------------- | -------- | ---------- | ---------------------------- |
| main                        | 검색하기     | **로그 검색**  | 로그 타입별 조건으로 DB 로그 검색         |
| search-history              | 검색 이력    | **이력·승인**  | 복호화 요청 이력 목록(요청자·일시·조건·승인상태) |
| activity-log                | 활동 이력    | **사용자·이력** | 사용자별 활동 로그 목록                |
| statistics                  | 활동로그 통계  | **통계**     | 사용자/부서/로그타입별 집계              |
| pending-approvals           | 승인 대기    | **이력·승인**  | 복호화 승인 대기 목록(요청자·조건·일시)      |
| user-management             | 사용자 관리   | **사용자·관리** | 부서별 사용자 계층 + 권한/결재자 편집       |
| permission-group-management | 권한 그룹 관리 | **사용자·관리** | 권한 그룹 목록 + 그룹별 사용자 할당        |

## 2. 도메인별 권장 검색 축(통일 기준)

### 2.1 사용자·요청자 맥락 (공통 3종)

**대상**: “누가 / 어떤 사용자”를 찾거나 필터하는 모든 화면.


| 검색 축         | 설명                    | 통일 시 기대 효과 |
| ------------ | --------------------- | ---------- |
| **부서**       | department_code / 부서명 | 부서 단위로 좁히기 |
| **이름(사용자명)** | username 표시명 / 성명     | 이름으로 찾기    |
| **사용자 ID**   | userId (로그인 ID)       | 정확히 한 명 지정 |


- **적용 화면**: 활동 이력, 통계, 사용자 관리, 권한 그룹 관리, 검색 이력, 승인 대기  
- 동일한 “사용자 관련 검색”이 필요한 화면에서는 위 세 가지를 **공통 기본**으로 두고, 화면별로 추가 축(IP, 액션 타입, 로그 타입 등)만 더 두는 방식으로 통일할 수 있음.

### 2.2 로그 검색 맥락 (main)

**대상**: 로그 타입별 DB 로그 검색(main).


| 검색 축          | 설명                                                 | 비고         |
| ------------- | -------------------------------------------------- | ---------- |
| **날짜(시작·종료)** | 검색 기간                                              | 공통         |
| **로그 타입**     | pb_feplog / java_fw_imglog 등                       | 화면 진입 시 선택 |
| **타입별 필드**    | media_gb, tr_code, loginId, application, service 등 | 타입별 스펙에 따름 |


- 로그 검색은 “사용자 검색”과 성격이 다르므로, **사용자 3종(부서·이름·사용자ID)** 와는 별도로 두고, 로그 타입·날짜·타입별 필드만 통일하면 됨.

### 2.3 이력·승인 맥락 (검색 이력 / 승인 대기)

**대상**: “누가 요청했는지(요청자)”가 중요한 목록.

- **검색 이력**: 본인/부서/전체 범위 내에서 “요청자” 기준 필터 필요.  
- **승인 대기**: 결재자 화면에서 “어떤 요청자의 건인지” 필터 필요.

→ 요청자 = 사용자이므로, **요청자(사용자 ID)·부서·이름**으로 통일하는 것이 일관됨.

### 2.4 Scope=self(본인만)인 경우 — 사용자·부서 검색 비적용

**대상**: activity-log, statistics 등 권한 그룹의 **scope가 'self'(본인만)** 인 화면.

- **정책**: 해당 화면에서는 **부서·사용자(사용자ID·사용자명)·IP 검색을 제공하지 않고**, 항상 로그인한 **본인**만 조회한다.
- **프론트**: 부서·사용자ID·사용자명·IP 필터 영역을 **같은 블록**으로 두고, `hideUserFilters === true`(scope=self)일 때 **해당 블록 전체 비표시**. 요청 시 해당 파라미터는 API에 보내지 않음.
- **백엔드**: scope=self일 때 요청의 userId/username/department/ip 등은 **무시**하고, 항상 **현재 사용자**로 고정해 조회.
- **통일 검색(부서·이름·사용자ID)** 은 **scope가 team 또는 all** 인 경우에만 적용한다.

## 3. 화면별 현황 및 통일 시 권장 검색 항목

### 3.1 요약 표


| 화면              | 부서  | 이름  | 사용자ID | 현재 비고                              | 통일 시 권장                          |
| --------------- | --- | --- | ----- | ---------------------------------- | -------------------------------- |
| **활동 이력**       | 없음  | O   | O     | IP, 액션타입 있음 / scope=self 시 필터 숨김   | 부서 추가 → 부서·이름·사용자ID + (IP, 액션타입) |
| **통계**          | O   | 없음  | O     | 로그타입, IP 있음 / scope=self 시 필터 숨김   | 이름 추가 → 부서·이름·사용자ID + (로그타입, IP) |
| **사용자 관리**      | 트리만 | 없음  | 없음    | 트리 확장으로만 조회                        | 부서·이름·사용자ID 검색 폼 추가(트리/목록 필터)    |
| **권한 그룹 관리**    | 없음  | 없음  | 선택만   | 그룹별 사용자 추가 시 userId 드롭다운만          | 부서·이름으로 사용자 목록 필터 후 선택           |
| **검색 이력**       | 없음  | 없음  | 없음    | 페이지/정렬만, 요청자 컬럼 없음(API에 userId 있음) | 요청자(사용자ID)·부서·이름 필터 추가           |
| **승인 대기**       | 없음  | 없음  | 없음    | 요청자 컬럼만, 필터 없음                     | 요청자(사용자ID)·부서·이름 필터 추가           |
| **main(로그 검색)** | -   | -   | -     | 로그 도메인 전용                          | 사용자 3종 불필요; 날짜·타입·타입별 필드만 유지     |


### 3.2 상세

- **활동 이력 (activity-log)**  
  - 현재: 사용자 ID, 사용자명, 액션 타입, IP. 부서 없음.  
  - 통일: **부서** 추가 → 부서·이름·사용자ID 동일하게 제공. (scope=self일 때는 기존처럼 사용자 필터 숨김 유지)
- **통계 (statistics)**  
  - 현재: 로그 타입, 사용자 ID, 부서, IP. 이름(사용자명) 없음.  
  - 통일: **이름(사용자명)** 추가 → 부서·이름·사용자ID 동일하게 제공.
- **사용자 관리 (user-management)**  
  - 현재: 부서 트리만, 이름/사용자ID 검색 없음.  
  - 통일: 상단에 **부서·이름·사용자ID** 검색 폼 추가 → 트리 또는 평면 목록을 해당 조건으로 필터.
- **권한 그룹 관리 (permission-group-management)**  
  - 현재: 그룹별 사용자 추가 시 전체 사용자 중 userId만 선택.  
  - 통일: **부서·이름**으로 후보 사용자 목록 필터 후, 사용자ID 선택(동일한 사용자 검색 패턴).
- **검색 이력 (search-history)**  
  - 현재: 검색 폼 없음, 페이지/정렬만. API에 요청자(userId) 정보 있음.  
  - 통일: **요청자(사용자ID)·부서·이름** 필터 추가(목록 API가 해당 파라미터 지원 시).
- **승인 대기 (pending-approvals)**  
  - 현재: 요청자 컬럼만 있고 필터 없음.  
  - 통일: **요청자(사용자ID)·부서·이름** 필터 추가(목록 API가 해당 파라미터 지원 시).
- **main (로그 검색)**  
  - 로그 도메인 전용. 사용자 검색 축과는 별도로, **날짜·로그 타입·타입별 필드**만 통일 유지.

## 4. 통일 시 기대 효과 및 적용 순서 제안

### 4.1 기대 효과

- **사용자 관련 화면**: 부서·이름·사용자ID를 공통으로 두어, 사용자관리·권한관리·활동이력·통계·검색이력·승인대기에서 **동일한 방식으로 사용자(또는 요청자)를 찾을 수 있음**.  
- **이력·승인 화면**: 검색 이력과 승인 대기에서 **요청자 기준 필터**를 동일한 3종(부서·이름·사용자ID)으로 맞출 수 있음.  
- **관리 화면**: 사용자 관리와 권한 그룹 관리에서 **같은 사용자 검색 패턴**으로 일관된 UX 제공.

### 4.2 적용 순서 제안(참고)

1. **백엔드**: 검색 이력 목록 API·승인 대기 목록 API에 요청자( userId )·부서·이름(또는 username) 필터 파라미터 지원 여부 확인 및 추가.
2. **공통**: “사용자 검색 3종(부서·이름·사용자ID)”을 재사용 가능한 컴포넌트 또는 훅으로 두고, 필요한 화면에 주입.
3. **화면별**:
  - 활동 이력: 부서 필드 추가.  
  - 통계: 이름(사용자명) 필드 추가.  
  - 사용자 관리: 검색 폼 추가 후 트리/목록 필터.  
  - 권한 그룹 관리: 사용자 추가 시 부서·이름 필터 추가.  
  - 검색 이력·승인 대기: 요청자·부서·이름 필터 폼 추가 및 API 연동.

---

## 5. 정리

- **사용자·요청자 맥락**이 있는 6개 화면(활동 이력, 통계, 사용자 관리, 권한 그룹 관리, 검색 이력, 승인 대기)에서는 **부서 + 이름(사용자명) + 사용자 ID**를 공통 검색 축으로 두고 통일하는 것이 적절함.  
- **로그 검색(main)**은 사용자 검색과 성격이 다르므로, 로그 타입·날짜·타입별 필드만 통일하면 됨.  
- 위 분석을 기준으로 API 스펙·컴포넌트 설계를 정한 뒤 단계적으로 적용하면, 화면별로 필요한 검색 기능을 통일할 수 있음.
- **Unified concept (동일 컨셉)**: UI 필드 순서·그룹핑·라벨 통일은 **`docs/requirements/20260310-search-ui-unify.md`** 참고 (부서 → 사용자명 → 사용자 ID, 단일 사용자 블록, 라벨 "사용자명").
