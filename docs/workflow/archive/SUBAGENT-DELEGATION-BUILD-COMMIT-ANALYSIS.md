# 서브에이전트 위임 시 빌드·커밋이 수행되지 않는 이유 분석

## 요약

- **빌드·재시작**: Step 4(Frontend/Backend) 서브에이전트 **역할에는 포함**되어 있으나, 호출 방식·프롬프트에 따라 생략되거나 메인 챗에서 대신 수행되는 경우가 있음.
- **커밋**: **어느 서브에이전트에도 배정되어 있지 않음.** 검증(§5/§6) 완료 **이후** 메인 에이전트가 수행하는 단계로 설계되어 있어, 서브에이전트만 사용하면 커밋이 자동으로 일어나지 않음.

---

## 1. 워크플로우상 역할 배정

### 1.1 위임 표(SUBAGENT-DELEGATION.md)

| Step | 서브에이전트 | 담당 범위 |
|------|----------------|-----------|
| 4 | Frontend / Backend / DB | 구현, **build, restart**, QA로 핸드오프 |
| 5 | QA | 검증(verify 체크리스트, 헬스체크), §5·§6 갱신 |
| 6 | Documentation / Release | 사용자 문서, CHANGELOG 등 |

**커밋은 위 표에 없음.**

### 1.2 체크리스트(WORKFLOW_CHECKLIST.md)

- 4단계: 개발
- 5단계: 단위 테스트 → §5 기록
- 6단계: 검증·재시작
- 7단계: 문서화 (§5·§6)
- **8단계: 해결 완료 시 Git commit** — `.cursor/commands/commit-on-complete.md` 따라 커밋

8단계(커밋)는 “검증 통과·문서 반영 후” 수행하도록 되어 있고, **어느 서브에이전트 이름이 붙어 있지 않음.**

### 1.3 post-change-test-verify.mdc

- 서브에이전트 위임으로 개발한 경우:  
  “QA 서브에이전트에게 Step 5 위임 … **QA 완료 후, 메인 에이전트가** commit-on-complete.md에 따라 **commit** 할 수 있다”고 명시.
- 즉, **커밋 수행 주체 = 메인 에이전트** (메인 챗).

## 2. 빌드·재시작이 “안 된 것처럼” 보일 수 있는 이유

### 2.1 설계상 기대

- **CURSOR-SUBAGENTS-DESIGN.md** §2:  
  Frontend는 코드/설정 변경 후 **반드시**  
  `cd frontend && npm run build` → `./scripts/dev-services.sh frontend restart` → QA에게 검증 위임.
- **Frontend.mdc** “After code changes”:  
  1) Build, 2) Restart, 3) QA 서브에이전트에게 검증 지시.

즉, **역할 정의상** Frontend 서브에이전트가 빌드·재시작까지 수행하는 것이 맞음.

### 2.2 실제로 빠지기 쉬운 경우

1. **메인 챗에서 mcp_task 등으로 호출할 때**  
   - “재시작은 하지 말고 빌드만 해줘”처럼 **재시작을 제외**하도록 지시한 경우, 서브에이전트는 빌드만 하고 재시작은 하지 않음.  
   - 그러면 “서브에이전트가 재시작까지 안 한다”로 느껴질 수 있음 (의도된 제외인지, 역할 인지 부족인지 구분 필요).

2. **사용자가 별도 챗에서 Frontend 서브에이전트로 전환해 작업할 때**  
   - 서브에이전트가 “코드 수정”만 하고 “After code changes” 절차(빌드·재시작)를 생략할 수 있음.  
   - 원인 후보:  
     - 사용자 질문이 “수정만 해줘”에 가까워 빌드·재시작까지 포함되지 않음  
     - 터미널 실행 권한/환경 차이  
     - 프롬프트 길이·맥락 때문에 “코드 변경 후 절차”가 누락됨  

3. **재시작을 QA나 메인 챗에서 하는 설계**  
   - “재시작은 메인/QA가 한다”고 명시해 두고 Frontend에는 “빌드만” 요청한 경우, 재시작은 메인 챗에서 하게 되므로, “서브에이전트가 재시작까지 안 한다”는 맞는 동작임.

## 3. 커밋이 수행되지 않는 이유 (핵심)

- **커밋은 서브에이전트 역할이 아님.**  
  SUBAGENT-DELEGATION 표·AGENT-COLLABORATION 시퀀스 모두에서 “commit”은 Step 4(Frontend/Backend), Step 5(QA), Step 6(Docs/Release)에 포함되어 있지 않음.

- **커밋은 “검증·문서 반영 후” 메인 챗에서 수행하는 단계로 설계됨.**  
  - `commit-on-complete.md`: 요건 해결 완료 시, 검증 통과·§5(·§6) 반영 후 커밋.  
  - `post-change-test-verify.mdc`: “QA 완료 후, **메인 에이전트가** commit-on-complete.md에 따라 commit.”

- 따라서 **서브에이전트만 사용하고 메인 챗에서 “커밋해줘”를 하지 않으면 커밋이 발생하지 않는 것이 설계와 일치**함.  
  “서브에이전트에게 위임해서 하는데 커밋까지 수행하지 않는다”는, **커밋이 서브에이전트 스코프에 없기 때문**에 발생하는 격차로 볼 수 있음.

---

## 4. 개선 방향 제안

### 4.1 빌드·재시작이 확실히 수행되도록

- **Frontend/Backend 호출 시** (메인 챗에서든, 사용자가 서브에이전트 챗에서 요청할 때든):  
  - “코드 변경 후 **반드시** build 실행하고, **restart**까지 수행한 뒤 QA에게 검증을 넘겨줘”라고 명시.  
- 서브에이전트용 프롬프트(예: `frontend.md`, `.cursor/agents/Frontend.mdc`)에  
  “코드/설정 변경이 있으면 **항상** build → restart → QA 위임 순서를 실행하고, 각 단계 결과(exit code, 재시작 완료 여부)를 한 줄로 보고한다”를 넣어 두면, 역할 인지가 더 일정해짐.

### 4.2 커밋까지 한 번에 끝나게 하려면

**옵션 A (현 설계 유지)**  
- 서브에이전트는 Step 4(구현·빌드·재시작)와 Step 5(검증·§5/§6)까지만 수행.  
- **메인 챗에서** “QA까지 끝났으니 이제 커밋해줘”라고 한 번 요청하거나, 메인 에이전트가 “QA 완료됐으니 commit-on-complete.md 따라 커밋 수행”하도록 규칙/체크리스트에 명시.

**옵션 B (커밋까지 위임하고 싶은 경우)**  
- SUBAGENT-DELEGATION 표에 **Step 5 이후** “Step 5.5 또는 7: **Commit**”을 두고,  
  - “QA가 §5/§6 갱신까지 완료한 뒤, **메인 에이전트**가 commit-on-complete.md에 따라 커밋한다”를 표에 명시하거나,  
  - 또는 “QA 서브에이전트 출력에 ‘검증 및 §5/§6 완료. 메인 에이전트는 commit-on-complete.md에 따라 커밋할 것.’ 문구를 포함한다”처럼, **QA 완료 → 메인 에이전트가 커밋**이라는 연결을 문서화.  
- 그러면 “서브에이전트 위임 후에도, 마지막에 메인 챗에서 커밋이 꼭 한 번 실행되어야 한다”가 명시되어, 사용자·메인 에이전트 모두가 커밋 단계를 빠뜨리기 어렵게 됨.

**옵션 C (Release 서브에이전트에 커밋 유도 문구)**  
- Release 서브에이전트는 CHANGELOG·릴리스 체크리스트만 담당하고, **코드 커밋은 하지 않음**이 현재 설계.  
- 대신 Release(또는 QA) 출력에 “로컬 커밋은 메인 에이전트가 commit-on-complete.md에 따라 수행”이라고 넣어, **커밋 책임이 메인 에이전트에 있음**을 반복해 알리면, 메인 챗에서 커밋이 수행될 확률이 높아짐.

## 5. 빌드·재시작 누락 방지 — 역할 분리 vs 역할 집중 개선 포인트

현재 **빌드·재시작**은 Step 4(Frontend/Backend)에 함께 넣여 있어, 구현 에이전트가 “코드만 수정”에 집중하면 누락되기 쉽다. 아래는 **역할 분리**와 **기존 에이전트 역할 집중**으로 개선할 수 있는 포인트다.

### 5.1 역할 분리: 빌드·재시작을 별도 단계/책임으로 두기

| 방안 | 설명 | 장점 | 단점 |
|------|------|------|------|
| **4a/4b 분리** | Step 4를 **4a 구현**(코드만) + **4b 빌드·재시작**(실행)으로 나눔. 4b는 **메인 에이전트**가 수행하거나, 사용자가 “구현 완료됐으니 빌드·재시작 해줘”라고 한 번 더 요청. | 구현 에이전트는 “코드 완료”만 내고, 빌드/재시작은 항상 다른 주체가 하므로 **누락 가능성 감소**. | 메인 챗에서 한 단계가 추가되거나, 사용자가 4b를 요청해야 함. |
| **전용 서브에이전트** | “Runner” 또는 “Build” 서브에이전트를 두어, 입력으로 “frontend 또는 backend, 요건 문서”를 받고 **빌드 + 재시작만** 수행한 뒤 QA로 넘김. Frontend/Backend는 구현만 하고 Runner에게 넘김. | 빌드·재시작이 **한 에이전트의 유일한 책임**이 되어 누락되지 않음. | 서브에이전트 수 증가; Cursor Settings에 새 에이전트 추가 필요. |

**정리**: 역할 분리는 “구현”과 “실행(빌드·재시작)”을 분리해, 구현 쪽이 빌드/재시작을 잊어도 **다른 단계/에이전트가 반드시 수행**하게 만든다.

---

### 5.2 역할 집중: 한 에이전트가 “빌드·재시작 보장”을 명확히 맡기

| 방안 | 설명 | 장점 | 단점 |
|------|------|------|------|
| **QA를 게이트로 강화** | QA 서브에이전트의 전제를 “**build and restart가 완료된 뒤에만** 검증 수행”으로 고정. 프롬프트에 다음을 명시: “입력에 ‘build and restart 완료’ 확인이 없으면, **먼저** 해당 레이어(frontend/backend)의 빌드·재시작을 자신이 실행하거나, 사용자/메인에게 ‘빌드·재시작 후 다시 QA를 호출해 달라’고 안내한 뒤 검증은 하지 않음.” | **QA가 마지막 관문**이 되어, Frontend가 빌드/재시작을 건너뛰어도 QA가 실행하거나 차단함. 기존 에이전트만으로 개선 가능. | QA가 터미널을 실행할 수 있어야 함; 역할이 “검증 + 빌드/재시작 보장”으로 넓어짐. |
| **Frontend/Backend 산출물을 “실행 확인” 포함으로 고정** | Frontend/Backend 에이전트의 **핸드오프 규칙**을 강화: “코드 변경이 있으면 반드시 **산출물 끝에** 다음 한 줄을 포함한다: ‘Build: [명령] exit [코드]. Restart: [명령] 완료. QA에게 검증 위임.’ 이 문구가 없으면 Step 4 미완료로 간주.” 메인/QA는 이 문구를 보고 “빌드·재시작 완료”를 인정. | 구현 에이전트가 빌드/재시작을 **실행하고 보고**하는 것이 명시적 계약이 됨. 새 에이전트 없이 규칙·프롬프트만 조정. | 에이전트가 실제로 실행하지 않고 문구만 쓸 수 있는 위험은 있음(정책으로 보완). |
| **메인 에이전트가 4 직후 항상 빌드·재시작** | 위임 표와 규칙에 “Step 4(Frontend/Backend) 완료 후, **메인 에이전트**가 반드시 해당 스코프(frontend|backend)의 빌드·재시작을 실행한 뒤 QA를 호출한다”고 명시. 구현 서브에이전트는 **코드만** 내고, 빌드·재시작은 메인 챗에서만 수행. | 빌드·재시작이 **한 주체(메인)**에만 있어 누락 가능성이 줄어듦. | 사용자가 메인 챗에서 Step 4 완료 후 다음 메시지를 주거나, 메인 에이전트가 자동으로 빌드/재시작을 수행해야 함. |

**정리**: 역할 집중은 “빌드·재시작을 **반드시** 수행하는 주체”를 하나로 정해 두는 것이다. **QA 게이트 강화**나 **메인 에이전트가 4 직후 빌드·재시작**이면 기존 에이전트만으로도 개선 가능하다.

### 5.3 권장 조합 (기존 에이전트 활용)

- **단기(규칙·프롬프트만)**  
  - **Frontend/Backend**: “After code changes”를 **필수 산출**로 묶어, “코드 변경 시 반드시 build + restart 실행 후, **출력에** ‘Build: … exit N. Restart: … 완료.’를 포함하고 QA 위임”이라고 `.cursor/agents/Frontend.mdc`(및 Backend)와 `docs/cursor-subagents/frontend.md`에 명시.  
  - **QA**: “입력에 ‘build and restart 완료’가 없으면 검증을 진행하지 말고, 먼저 빌드·재시작을 실행하거나 사용자에게 그렇게 요청하라”를 QA.mdc와 qa-test.md에 추가.  
  → 구현 쪽은 “실행+보고”가 의무이고, QA는 “미완료 시 자신이 실행하거나 차단”하는 **이중 안전장치**.

- **중기(역할 분리)**  
  - Step 4를 **4a 구현(코드)** / **4b 빌드·재시작**으로 문서상 분리하고, 4b는 **메인 에이전트**가 “Step 4a 완료 알림 후” 수행하도록 `SUBAGENT-DELEGATION.md`·`AGENT-COLLABORATION-ON-REQUIREMENT.md`에 넣음.  
  → 구현 에이전트는 빌드/재시작 책임에서 해제되고, 누락은 구조적으로 방지됨.

---

## 6. 메인 에이전트를 “위임 전용”으로 지정하기

**가능 여부**: 가능하다. 메인 에이전트를 **다른 역할 없이** 사용자 요청을 받아 서브에이전트에게 전달·위임만 하도록 지정할 수 있다.

### 6.1 위임 전용 메인 에이전트의 역할

| 할 일 | 설명 |
|--------|------|
| **수신** | 사용자 요청(요건, 기능, 오류 수정 등)을 받는다. |
| **판단** | 요청에 필요한 단계(1→2→3→4→5→6)와 해당 서브에이전트를 판단한다. |
| **위임** | 사용자에게 “○○ 서브에이전트로 전환하고, 아래 입력을 전달하라”고 안내하고, **전달할 입력 문장**과 **기대 출력**을 적어 준다. |
| **하지 않음** | 요건 문서 작성, 구현, 빌드·재시작, 검증, §5/§6 갱신, 커밋 등 **어느 단계의 실행도 하지 않는다.** (예외: 사용자가 “이 챗에서만 해줘”라고 할 때만 해당 단계 수행.) |

이렇게 하면 메인 에이전트는 **라우터/오케스트레이터**만 담당하고, 실제 작업은 전부 서브에이전트(또는 사용자)가 한다.

### 6.2 조정이 필요한 부분: 커밋

현재 **커밋**은 서브에이전트에 배정되어 있지 않고, “QA 완료 후 메인 에이전트가 commit-on-complete.md에 따라 커밋”으로 되어 있다. 메인 에이전트를 위임 전용으로 두면 메인은 커밋을 하지 않으므로, 아래 중 하나로 정해야 한다.

| 옵션 | 설명 |
|------|------|
| **A. QA에 커밋까지 위임** | QA 서브에이전트의 “검증 및 §5/§6 갱신” 후, **같은 QA가** commit-on-complete.md에 따라 `git add` / `git commit`까지 수행하도록 역할에 넣는다. (push는 사용자 요청 시에만.) |
| **B. Release에 커밋 문구·안내** | Release 서브에이전트는 코드를 수정하지 않으므로, “CHANGELOG·체크리스트 갱신 후, **커밋은 사용자가** commit-on-complete.md에 따라 수행”이라고 출력에 포함시킨다. 메인은 커밋하지 않고, **사용자가** QA/Release 완료 후 직접 커밋. |
| **C. 사용자 액션으로 고정** | 위임 표·규칙에 “모든 단계는 서브에이전트가 수행하며, **로컬 커밋은 사용자가** 검증·§5/§6 완료 후 commit-on-complete.md에 따라 수행한다”고 명시. 메인 에이전트는 커밋을 시도하지 않는다. |

원하면 **A**로 가면 “메인은 위임만, 커밋까지 서브에이전트(QA)”로 완전히 갈 수 있고, **B/C**로 가면 “메인은 위임만, 커밋은 사용자”로 정리할 수 있다.

### 6.3 규칙·문서에 반영할 내용

- **`.cursor/rules/agent-collaboration.mdc`** (또는 메인 에이전트용 규칙):  
  “메인 에이전트는 **위임 전용**이다. 사용자 요청을 받아 필요한 단계와 서브에이전트를 판단하고, 사용자에게 전환할 서브에이전트와 전달할 입력을 안내한다. 요건 문서 작성, 구현, 빌드·재시작, 검증, §5/§6 갱신, 커밋 등 단계 실행은 **서브에이전트 또는 사용자**가 수행한다. 예외: 사용자가 ‘code only here’ / ‘skip subagent’ / ‘do it in this chat’이라고 한 경우에만 해당 단계를 메인 챗에서 수행할 수 있다.”
- **`docs/workflow/SUBAGENT-DELEGATION.md`**  
  - §2 Main agent behavior에 “메인 에이전트는 위임 전용(identify → instruct user to switch + pass input). 단계 실행(요건 문서, 구현, 빌드·재시작, 검증, §5/§6, 커밋)은 하지 않는다.”를 추가.  
  - 커밋을 QA 또는 사용자에게 넘기기로 했다면, 위임 표나 “Step 5 이후” 문단에 “로컬 커밋: QA가 수행” 또는 “로컬 커밋: 사용자가 commit-on-complete.md에 따라 수행”을 명시.

이렇게 지정하면 메인 에이전트는 **다른 역할 없이** 사용자 요청을 서브에이전트에게 전달·위임만 하도록 동작하게 할 수 있다.
