# Sub-Agent 동작 방식 정리

## 사용자가 원했을 수 있는 것 vs 현재 구현

| 기대 (예시) | 현재 구현 | 차이 |
|-------------|-----------|------|
| **"Sub-agent로 동작"** = 내가 **프론트 sub-agent를 선택**하면, **그 채팅에서 응답하는 주체가 프론트 sub-agent**다. 그 에이전트와 직접 대화하는 느낌. | **메인 에이전트**가 항상 대화 상대. Sub-agent는 (1) 규칙으로 역할만 적용하거나 (2) **일회성** mcp_task 실행 후 결과만 메인 에이전트가 전달. | **대화 주체**가 사용자 기대와 다름. 사용자는 "sub-agent가 응답한다"를 원했을 수 있음. |
| Sub-agent를 **선택/전환**해서 그 에이전트 모드로 계속 작업. | 역할 전환은 `/agent-frontend` 등으로 "지금부터 역할 제한"만 함. Cursor 설정의 "Subagent"에 별도 에이전트가 등록된 것은 아님. | Cursor Settings에 sub-agent가 안 보이는 이유와 맞음. |

## 현재 구조 요약

1. **역할 규칙** (frontend-agent.mdc 등)  
   - `frontend/**` 파일을 다룰 때만 적용.  
   - **동작**: 같은 에이전트가 "프론트만 수정" 규칙을 적용해 응답. → "sub-agent로 동작"이 아니라 "같은 에이전트가 역할 제한된 모드".

2. **역할 커맨드** (/agent-frontend, /agent-backend, /agent-db)  
   - "지금부터 이 채팅에서 프론트(또는 백엔드/DB) 전용으로만 동작해줘"라고 지시.  
   - **동작**: 같은 에이전트가 그 역할을 유지. → **채팅에서 sub-agent처럼 동작**시키려면 이걸 쓰는 게 맞음.

3. **mcp_task 위임** (/run-frontend-agent 등, "맡겨줘")  
   - **별도 에이전트**가 한 번 실행되고, 결과만 메인 에이전트가 전달.  
   - **동작**: 사용자와 직접 대화하는 건 여전히 **메인 에이전트**. Sub-agent는 "일회성 작업 실행자".

---

## 결론: "Sub-agent로 동작"에 가깝게 쓰는 방법

- **"이 채팅에서는 내가 프론트 sub-agent와 대화한다"** 느낌을 원하면:  
  **`/agent-frontend`** (또는 `/agent-backend`, `/agent-db`)를 **먼저 실행**한 뒤, 그 다음부터 할 일을 말하면 됨.  
  → 그 순간부터 에이전트는 "나는 프론트 sub-agent다"라고 하고, 그 역할만 유지하면 **sub-agent로 동작**하는 것과 비슷하게 됨.

- **"일회성으로 프론트만 맡겨서 실행"**을 원하면:  
  **`/run-frontend-agent`** 또는 "이 작업 프론트 sub-agent한테 맡겨줘" 사용.  
  → 별도 프로세스가 돌고 결과만 돌아오는 방식이라, "동작" 주체는 메인 에이전트.

즉, **요구하신 "sub-agent로 동작"**은 **역할 커맨드(/agent-*)** 로 맞추는 것이 맞고, **현재 그 방식이 요구와 다르게 느껴졌다**면 "동작 주체"가 메인 에이전트라서 그런 것입니다. 아래에서 역할 커맨드를 더 강하게 조정할 수 있습니다.
