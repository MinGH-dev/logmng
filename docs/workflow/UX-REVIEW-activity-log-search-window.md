# UX 검토 — 사용자 활동 이력 검색/필터 영역

**대상 화면**: 사용자 활동 이력 (User Activity Log)  
**검토 범위**: 상단 검색 폼(Row 1: 날짜, Row 2: 사용자·기타 조건·버튼)  
**검토일**: 2026-03-11  
**참조**: `docs/design/forms-and-filters.md`, `docs/design/buttons.md`, `docs/design/text-input.md`, `docs/design/date-search.md`, `docs/design/UX-REDESIGN-activity-log-statistics-search.md`  
**목적**: 설계/UX 권고만 제시. 코드 수정 없음. Frontend 핸드오프용 문서.

---

## 1. 심각도 및 종합 평가

**수준: 보통(Moderate)**

전반적으로 설계 표준(forms-and-filters, buttons, date-search)과 요구사항(2행 레이아웃, 사용자 컨텍스트 순서)은 대체로 맞추어져 있고, 검색/초기화 버튼·폼 시맨틱·날짜 검증·라벨은 잘 반영되어 있다. 다만 **Row 2에 한 행에 너무 많은 요소가 몰려** 정보 계층이 약하고, **접근성·시맨틱·시각적 무게** 측면에서 개선이 필요한 이슈가 여러 개 있다. 특히 좁은 뷰포트에서의 줄바꿈·버튼 위치·그룹 라벨·입력 폭/힌트는 사용성과 a11y에 직접 영향을 준다. 치명적 결함은 아니지만, 우선순위가 높은 3~5개 항목을 고치면 체감 품질이 크게 좋아질 수 있다.

## 2. 문제 목록 (구체적 UX 이슈)

### 2.1 레이아웃·정보 계층

| # | 문제 | 위치 | 이유 |
|---|------|------|------|
| P1 | **Row 2 요소 과다** | Row 2 전체 | 한 행에 사용자 블록(부서·사용자명·사용자 ID) + "기타 조건" 제목 + 액션 타입 + IP + 검색·초기화가 모두 나란히 있어, 스캔 순서와 논리적 그룹이 한눈에 들어오지 않음. `forms-and-filters.md`의 "그룹별 블록·명확한 구분"과 다소 어긋남. |
| P2 | **"기타 조건"과 사용자 블록의 시각적 구분 부족** | Row 2, 사용자 블록 ~ 기타 조건 사이 | 사용자(부서·이름·ID)와 기타 조건(액션 타입·IP)이 같은 flex 행에 붙어 있어, 그룹 경계가 시각적으로만으로는 구분되기 어려움. 표준의 "블록 간 16–24px 간격 또는 헤딩으로 구분"과 맞추면 좋음. |
| P3 | **날짜 행과 Row 2 간 위계 약함** | Row 1 ↔ Row 2 | 두 행이 같은 배경·같은 패딩으로 이어져 있어, "날짜가 최상위 조건"이라는 인지가 약함. (선택) Row 1에만 얕은 구분선이나 약한 배경 차이를 두면 계층이 더 분명해짐. |

### 2.2 간격·터치 타겟·반응형

| # | 문제 | 위치 | 이유 |
|---|------|------|------|
| P4 | **좁은 뷰포트에서 버튼 위치 불안정** | Row 2, 검색·초기화 | 1099px 이하에서 `.search-form-actions`가 `width: 100%`로 줄바꿈되지만, "다음 줄 왼쪽"에 오는지 "오른쪽 정렬"인지 일관된 패턴이 없으면 사용자가 버튼을 찾기 어려움. `forms-and-filters.md`·`buttons.md`의 "주요 액션 한 곳에 고정"과 맞추는 것이 좋음. |
| P5 | **컴팩트 변형에서 행/블록 간격** | Row 1–Row 2, Row 2 내부 | 표준은 행 간 8–12px, 블록 간 12–16px. 현재 Row 1 `margin-bottom: 10px`은 적절하나, Row 2 내부 사용자 블록 ↔ 기타 조건 간격이 10px gap만으로는 "다른 블록"임을 강조하기에 부족할 수 있음. |

### 2.3 입력·라벨·어포던스

| # | 문제 | 위치 | 이유 |
|---|------|------|------|
| P6 | **사용자명 5자 제한에 대한 시각적 힌트 부족** | 사용자명 입력 | `maxLength={5}`만 있고 placeholder는 "사용자명". `text-input.md`에 "placeholder에 필수 규칙만 두지 말고 라벨/보조 문구로"라고 되어 있음. 5자 한글 제한을 라벨 옆 또는 placeholder/보조 텍스트로 안내하면 오류를 줄일 수 있음. |
| P7 | **사용자 ID 8자리 제한 안내** | 사용자 ID 입력 | `aria-label="사용자 ID (숫자 8자리)"`는 있으나, 시각적으로 "숫자 8자리"가 보이지 않음. 시각 사용자에게는 라벨 옆 또는 placeholder로 "8자리"를 명시하는 것이 좋음. |
| P8 | **날짜 라벨이 "날짜"만 표기** | Row 1, 시작/종료 | `datetime-local` 사용 시 "시작 날짜"·"종료 날짜"만으로는 "시간 포함"이 드러나지 않음. `date-search.md`의 "시작/종료 일시" 라벨 권고와 맞추면 "시작 일시"·"종료 일시" 등으로 통일하는 것이 좋음. |

### 2.4 버튼·액션

| # | 문제 | 위치 | 이유 |
|---|------|------|------|
| P9 | **로딩 시 버튼 라벨만 변경** | 검색 버튼 | "검색 중..."으로 텍스트가 바뀌면 스크린 리더는 인지하나, 시각적으로는 버튼이 비활성화된 것만으로는 "요청 처리 중"이 명확하지 않을 수 있음. (선택) 스피너 아이콘 또는 `aria-busy` 등으로 보조 표현을 두면 일관성·접근성 모두 개선. |
| P10 | **초기화 버튼의 위험성 전달** | 초기화 버튼 | 현재 secondary 스타일로 적절하나, "초기화"가 "현재 조건을 모두 지우고 오늘 날짜로 재검색"이라는 점을 툴팁이나 보조 문구로 한 번 더 안내하면 실수 방지에 도움. (구현은 Frontend 선택.) |

### 2.5 접근성·시맨틱

| # | 문제 | 위치 | 이유 |
|---|------|------|------|
| P11 | **Row 2의 role="group" 라벨 불일치** | Row 2, `aria-labelledby="activity-log-search-screen-heading"` | `activity-log-search-screen-heading`이 "기타 조건"인데, 이 group에는 "사용자" 블록 전체도 포함됨. 그룹 라벨이 "기타 조건"이면 스크린 리더는 Row 2 전체가 "기타 조건"으로만 인식할 수 있어, "사용자" 블록과 혼동 가능. 그룹을 나누거나 라벨을 "검색 조건" 등 상위 개념으로 바꾸는 것이 좋음. |
| P12 | **폼 영역의 접근 가능한 이름** | `activity-log-search-form` | `<form>`에 `aria-label` 또는 `<legend>`/제목이 없으면, 스크린 리더가 "폼"만 알려주고 목적을 알기 어려움. "사용자 활동 이력 검색 조건" 등으로 폼에 접근 가능 이름을 부여할 것을 권고. |
| P13 | **날짜 오류 메시지 중복 노출** | Row 1, 종료 날짜 아래 | `dateRange` 오류가 시작/종료 둘 다 아래에 나올 수 있는 구조일 때, 동일 문구가 두 번 읽히면 불필요한 반복. 한 곳에만 오류를 노출하고 두 입력 모두 `aria-describedby`로 그 한 ID를 참조하는 방식이 `text-input.md`·`date-search.md`와 잘 맞음. |

### 2.6 일관성·시각적 무게

| # | 문제 | 위치 | 이유 |
|---|------|------|------|
| P14 | **"기타 조건"이 h4로만 구분** | Row 2, 기타 조건 제목 | 인라인 스타일로 행 안에 섞여 있어, 다른 화면의 "사용자" 블록 legend·필터 그룹 제목과 시각적 위계가 다를 수 있음. `forms-and-filters.md`의 그룹 제목 스타일을 통일하면 화면 간 일관성이 좋아짐. |
| P15 | **필터 접기 없음** | 전체 폼 | 요구사항상 "필터 접기 없음"이 맞음. 다만 표준은 "선택: 접을 수 있는 필터, 접었을 때도 검색/적용 버튼은 도달 가능"을 권고. 향후 요구가 생기면 접기 도입 시 a11y(aria-expanded, aria-controls)를 함께 설계할 것. (현재는 개선 권고만.) |

## 3. 우선순위 (먼저 손댈 3~5개)

| 순위 | 이슈 | 이유 |
|------|------|------|
| 1 | **P11 (Row 2 group 라벨 불일치)** | 스크린 리더 사용자에게 Row 2가 "기타 조건"으로만 읽혀 사용자 블록과 혼동될 수 있음. 시맨틱 수정만으로 영향이 큼. |
| 2 | **P12 (폼 접근 가능 이름)** | 폼 목적을 보조 기술이 알 수 있게 하면 검색 화면 전체 이용성이 개선됨. |
| 3 | **P1 또는 P2 (Row 2 과밀·그룹 구분)** | 사용자 블록과 기타 조건을 시각적으로 구분하면 스캔 속도와 인지 부하 개선. (P2만으로도 그룹 간격/헤딩으로 처리 가능.) |
| 4 | **P6·P7 (사용자명 5자·사용자 ID 8자리 힌트)** | 입력 오류와 재시도 감소. 표준(`text-input.md`)과도 부합. |
| 5 | **P8 (날짜 라벨을 일시로)** | `date-search.md`와의 일관성 및 "시간 포함" 인지 개선. |

## 4. 권고 사항 (구성요소/블록 수준, 코드 없음)

### 4.1 설계 문서 참조

- **폼·필터 구조**: `docs/design/forms-and-filters.md` — 그룹별 블록, Submit/Reset, 사용자 컨텍스트 순서(부서→사용자명→사용자 ID), 컴팩트 변형.
- **버튼**: `docs/design/buttons.md` — 1차(검색)/2차(초기화), 터치 타겟 최소 44×44px, 포커스 링, 접근 가능 이름.
- **텍스트 입력**: `docs/design/text-input.md` — 라벨 연동, placeholder 보조, 오류 시 aria-invalid·aria-describedby, 필수 표시.
- **날짜 검색**: `docs/design/date-search.md` — 시작≤종료 검증, 라벨("시작/종료 일시"), 오류 연동.
- **활동 이력·통계 검색 리디자인**: `docs/design/UX-REDESIGN-activity-log-statistics-search.md` — 검색/초기화 라벨, 버튼 위치, 폼 시맨틱.

### 4.2 블록/구성요소 수준 권고

1. **폼 접근 가능 이름**  
   `<form>`에 `aria-label="사용자 활동 이력 검색 조건"` 또는 동등한 이름을 부여. (Frontend 구현.)

2. **Row 2 그룹 시맨틱**  
   - 옵션 A: Row 2를 "검색 조건" 하나의 group으로 두고 `aria-labelledby`를 "검색 조건" 제목으로 연결.  
   - 옵션 B: "사용자" 블록(fieldset)과 "기타 조건"을 별도 `role="group"`으로 나누고, 각각 올바른 라벨 연결.  
   현재는 "기타 조건"이 Row 2 전체의 라벨로 쓰이지 않도록 정리할 것.

3. **사용자 블록 ↔ 기타 조건 시각 구분**  
   `forms-and-filters.md`에 따라 사용자 블록과 기타 조건 블록 사이에 12–16px 간격 또는 구분선을 두어, 한 행 안에서도 논리적 그룹이 보이도록 할 것.

4. **입력 힌트**  
   - 사용자명: 라벨 옆 또는 placeholder/보조 텍스트에 "최대 5자" 등 제한 안내.  
   - 사용자 ID: 시각용 라벨 또는 placeholder에 "8자리 숫자" 명시.  
   `text-input.md`의 "placeholder에 필수 규칙만 두지 말 것"에 맞춤.

5. **날짜 라벨**  
   "시작 날짜"·"종료 날짜"를 "시작 일시"·"종료 일시"로 변경해 `date-search.md` 및 실제 `datetime-local` 동작과 맞출 것.

6. **날짜 오류 메시지**  
   시작≤종료 위반 시 메시지는 한 곳(예: Row 1 하단)에만 표시하고, 시작/종료 입력 모두 `aria-describedby`로 그 영역을 참조하도록 할 것.

7. **버튼 위치 (좁은 뷰포트)**  
   줄바꿈 시 검색·초기화가 다음 줄로 갈 때, 항상 같은 정렬(예: 왼쪽 정렬)과 간격을 유지해 `buttons.md`의 "일관된 배치"를 따를 것.

8. **(선택) 로딩 상태**  
   검색 버튼에 "검색 중..." 텍스트 외 스피너 또는 `aria-busy="true"` 등 보조 표현을 두면 접근성·일관성 개선.

### 4.3 구현 주체

- 위 권고는 **Frontend**가 구현. UX는 설계·검토만 제공.
- API·백엔드 변경은 권고에 포함하지 않음. (UX 관점에서 백엔드 필요사항이 생기면 별도 요구사항으로 정리.)

## 5. 후속 피드백 (사용자·개발 반영)

- **기타 조건 위치/그룹핑**  
  공통 규칙: **`docs/design/forms-and-filters.md` §Filter group title placement** 참조. (그룹 제목은 필드 위에 배치; 인라인 제목은 표준 위반.)

- **입력 창 크기 유연성**  
  사용자 요청: 입력 창 크기를 유연하게.  
  **권고**: 고정 `max-width`(6em/9em) 대신 `min-width`만 보장하고 `width: 100%`·`flex: 1 1 auto` 등으로 가용 공간에 따라 폭이 늘어나거나 줄어들 수 있게 할 것. 적용: UserContextFilterBlock compact 입력, Row 1 날짜, Row 2 기타 조건 블록 내 입력.
