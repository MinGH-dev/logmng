# 개발 워크플로우 가이드

**순서만 빠르게 보려면**: `WORKFLOW_CHECKLIST.md` (같은 폴더). 규칙·스킬은 체크리스트와 이 문서를 **참조**하는 방식으로 두어 정확도를 유지한다.

## 📋 개요

이 문서는 로그 관리 시스템의 개발 워크플로우를 정의합니다. 모든 개발 작업은 이 가이드를 따라 수행되어야 합니다.

## 🔄 개발 원칙

### 0. 개발 환경 원칙 (최우선)

**⚠️ 중요: 모든 개발 작업은 `dev/` 디렉토리 내에서만 수행해야 합니다.**

- ✅ **DO**: `dev/frontend/`, `dev/backend/` 디렉토리에서만 개발 작업 수행
- ✅ **DO**: `docs/requirements/`, `specs/`, `docs/workflow/` 등에 개발 문서 생성 (이 프로젝트는 워크스페이스 루트가 dev)
- ✅ **DO**: 개발 완료 후 검증을 거쳐 배포
- ❌ **DON'T**: `prod/` 디렉토리에 직접 수정 (존재 시)
- ❌ **DON'T**: 요건·스펙 문서를 규칙·커맨드와 다른 경로에 생성 (단일 진실: `docs/requirements/`, `specs/`)

**이 프로젝트(dev) 문서 구조:**
```
dev/                        # 워크스페이스 루트
├── frontend/               # 프론트엔드
├── backend/                # 백엔드
├── docs/
│   ├── requirements/       # ✅ 요건 문서 (yyyyMMdd-요건명.md)
│   ├── workflow/           # 워크플로우 가이드
│   └── template/           # 요건·bugfix·오류조치 템플릿
├── specs/                  # ✅ 스펙 문서 (*.spec.yaml)
└── scripts/
```

**작업 시작 전 확인사항:**
1. 요건 문서는 `docs/requirements/`, 스펙은 `specs/`에 두는지 확인
2. `docs-reference.mdc`·`WORKFLOW_CHECKLIST.md`와 경로 일치 여부 확인

### 1. 기존 코드 보존 원칙

**모든 개발 작업은 기존 소스코드를 유지하고, 신규 코드로 대체합니다.**

- ✅ **DO**: 기존 파일을 복사하여 새 파일 생성 (예: `LogGrid.js` → `LogGrid.new.js`)
- ✅ **DO**: 기존 코드를 주석 처리하고 신규 코드 추가
- ✅ **DO**: Git 브랜치를 사용하여 변경사항 관리
- ❌ **DON'T**: 기존 파일을 직접 수정
- ❌ **DON'T**: 기존 코드를 삭제

**복구 방법:**
- 신규 파일 삭제 후 기존 파일 사용
- 주석 처리된 기존 코드 주석 해제
- Git 브랜치에서 이전 커밋으로 복구

### 2. 문제 발생 시 조치 방법

#### 상황 A: 요건은 정상 반영되었으나 Side Effect 발생

```
기존 코드 → 신규 코드 (요건 반영 ✅, Side Effect ❌)
```

**조치 절차:**
1. 즉시 기존 코드로 롤백
2. 영향도 분석 재수행
   - Side Effect 발생 원인 분석
   - 영향받는 기능 목록 작성
   - 대안 설계 검토
3. 개선된 신규 코드 작성
4. 재검증 수행

#### 상황 B: 요건이 정상 반영되지 않음

```
기존 코드 → 신규 코드 (요건 반영 ❌)
```

**조치 절차:**
1. 신규 코드에서 개선 작업 수행
2. 요건 재분석 및 설계 재검토
3. 테스트 케이스 보완
4. 재검증 수행

### 3. 개발 후 검증 단계 (필수)

#### 프론트엔드 검증

**검증 항목:**
- [ ] API 전달 파라미터 검증
  - 브라우저 콘솔에서 네트워크 요청 확인
  - `console.log`로 전송 데이터 확인
  - 필수 파라미터 누락 여부 확인
  - 파라미터 타입 및 형식 확인

**검증 방법:**
```javascript
// ImageLogSearchForm.js 또는 LogGrid.js에서
console.log('🔍 API로 전송할 데이터:', requestData);
console.log('🔍 datastring 값 확인:', requestData.datastring);
```

#### 백엔드 검증

**검증 항목:**
- [ ] API 파라미터 테스트 케이스 작성
- [ ] 단위 테스트 실행
- [ ] 통합 테스트 실행
- [ ] 로그 확인 (요청 파라미터, 처리 결과)

**검증 방법:**
```bash
# curl을 사용한 API 테스트
curl -X POST http://localhost:9200/api/logs/db-refactored/search \
  -H "Content-Type: application/json" \
  -d '{
    "logType": "java_fw_imglog",
    "startDate": "2026-02-01 00:00:00",
    "endDate": "2026-02-06 23:59:59",
    "datastring": "test",
    "page": 1,
    "pageSize": 10
  }'

# 백엔드 로그 확인
tail -f dev/backend/logs/application.log | grep -E "요청|파라미터|검색"
```

### 4. 요건 문서화

**요건 발생 시마다 문서를 작성합니다.**

**⚠️ 중요: 요건·스펙 문서 경로는 규칙·커맨드와 동일하게 유지합니다.**

#### 파일명 규칙
```
docs/requirements/yyyyMMdd-요건명.md
specs/요건명.spec.yaml
```

예시:
- `docs/requirements/20260206-image-log-datastring-search.md`
- `docs/requirements/20260206-user-authentication-improvement.md`
- `specs/user-management.spec.yaml`
- `specs/advanced-search.spec.yaml`

**문서 종류별 위치:**
- 요건 문서: `docs/requirements/`
- 스펙 문서: `specs/` (워크스페이스 루트)
- 워크플로·템플릿: `docs/workflow/`, `docs/template/`

#### 요건(Requirements) vs 스펙(Spec) 구분 기준

**요건 문서 (Requirements) - `docs/requirements/`**
- **목적**: 사용자의 비즈니스 요구사항과 문제 정의
- **내용**:
  - 사용자가 무엇을 원하는지 (What)
  - 왜 필요한지 (Why)
  - 사용자 시나리오 및 사용 사례
  - 비즈니스 목표 및 기대 효과
  - 제약사항 및 우선순위
- **대상 독자**: 비즈니스 이해관계자, 프로젝트 관리자, 개발자
- **작성 시점**: 요건 수집 및 분석 단계
- **예시**:
  - "사용자 관리 기능이 필요합니다"
  - "로그인 시 AD 연동이 필요합니다"
  - "전산요청서를 업로드해야 합니다"

**스펙 문서 (Specification) - `specs/`**
- **목적**: 기술적 설계 및 구현 명세
- **내용**:
  - 어떻게 구현할지 (How)
  - API 엔드포인트 및 요청/응답 형식
  - 데이터 모델 및 스키마
  - 알고리즘 및 로직 설계
  - UI/UX 상세 설계
  - 보안 및 성능 요구사항
  - 테스트 계획
- **대상 독자**: 개발자, 아키텍트, QA
- **작성 시점**: 설계 단계 (요건 문서 작성 후)
- **예시**:
  - API 명세: `POST /api/users`, 요청/응답 스키마
  - 데이터베이스 스키마: `users` 테이블 구조
  - UI 컴포넌트 설계: 사용자 관리 폼 레이아웃

**구분 기준 요약:**

| 구분 | 요건 (Requirements) | 스펙 (Specification) |
|------|---------------------|---------------------|
| **질문** | 무엇을, 왜 | 어떻게 |
| **관점** | 비즈니스/사용자 | 기술/구현 |
| **수준** | 추상적, 개념적 | 구체적, 기술적 |
| **포함 내용** | 목표, 시나리오, 제약 | API, 스키마, 알고리즘 |
| **작성 순서** | 먼저 작성 | 요건 기반으로 작성 |
| **변경 빈도** | 상대적으로 낮음 | 구현 과정에서 조정 가능 |

**작성 가이드:**
1. **요건 문서 먼저 작성**: 사용자 요구사항을 명확히 정의
2. **스펙 문서는 요건 기반**: 요건 문서를 바탕으로 기술적 설계 작성
3. **요건 변경 시 스펙 재검토**: 요건이 변경되면 스펙도 함께 업데이트
4. **복잡한 기능은 스펙 필수**: API, 데이터베이스 변경, 주요 기능은 스펙 문서 작성 권장

#### 문서 구조

```markdown
# yyyyMMdd - 요건명

## 1. 사용자 요건 내용
- 요건 설명
- 사용자 시나리오
- 기대 결과

## 2. 설계
- 기술 설계
- 변경 파일 목록
- 데이터베이스 변경사항 (해당 시)

## 3. 테스트 수행 방안
- 테스트 시나리오
- 테스트 데이터
- 테스트 환경

## 4. 체크리스트
- [ ] 프론트엔드 검증 완료
- [ ] 백엔드 검증 완료
- [ ] 통합 테스트 완료
- [ ] 문서화 완료

## 5. 테스트 결과
- 테스트 수행 일시
- 테스트 결과
- 발견된 이슈 및 해결 방법
```

## 📝 개발 워크플로우

### Step 1: 요건 수집 및 분석

1. 사용자 요건 확인
   - 사용자가 무엇을 원하는지 파악 (What)
   - 왜 필요한지 이해 (Why)
   - 사용자 시나리오 수집
2. 기존 코드 분석
3. 영향도 분석
4. **요건 문서 작성** (`docs/requirements/yyyyMMdd-요건명.md`)
   - 비즈니스 요구사항 문서화
   - 사용자 시나리오 및 기대 효과 기록
5. **스펙 문서 작성** (`specs/요건명.spec.yaml`, 복잡한 기능의 경우)
   - 요건 문서를 바탕으로 기술적 설계 작성
   - API 명세, 데이터 모델, UI 설계 등 포함
   - 단순한 기능은 스펙 생략 가능 (요건 문서만으로 충분한 경우)

### Step 2: 설계·테스트 계획 (개발 전 필수)

1. 기술 설계 작성
2. 변경 파일 목록 작성
3. 신규 코드 작성 계획 수립
4. **테스트 계획 수립**: 요건 문서 **§3 테스트 수행 방안**에 **테스트 케이스 목록**(정상/예외/엣지, 검증 기준)을 **지금** 작성한다. **개발(Step 3)에 착수하기 전에** 반드시 완료. **개발이 끝난 뒤에** §3을 채우지 않는다.

### Step 3: 개발 (1·2 완료 후에만 착수)

1. **기존 코드 백업**
   ```bash
   # Git 브랜치 생성
   git checkout -b feat/요건명
   
   # 기존 파일 복사
   cp src/components/LogGrid.js src/components/LogGrid.old.js
   ```

2. **신규 코드 작성**
   - 기존 파일을 복사하여 신규 파일 생성
   - 또는 기존 코드를 주석 처리하고 신규 코드 추가
   - 변경 이력 주석 추가

3. **코드 리뷰**
   - 코드 스타일 확인
   - 로직 검증
   - 에러 처리 확인

### Step 4: 테스트·검증

**4.0 단위/통합 테스트 실행 (신규 요건·오류 조치 구분 없이 필수)**  
- §3 테스트 계획은 **Step 2에서 이미 작성**되어 있어야 한다. (개발 후에 §3을 채우지 않음.)  
- **단위 테스트**: 백엔드 `mvn test`, 프론트 `npm test -- --watchAll=false` 실행. 실패 시 수정 후 재실행.  
- **통합 테스트**: 있으면 실행; 없으면 curl·수동 시나리오로 검증하고 요건 문서 §5에 기록.  
- 이 단계를 건너뛰지 않는다. 커맨드: `/run-tests`.

**4.1 재시작·정상 실행 확인 (자동, 사용자 요청 불필요)**  
- 에이전트가 **변경 범위**에 따라 `./scripts/dev-services.sh frontend|backend|db|all restart` 를 실행한 뒤, health·포트·DB 응답을 **자동 확인**한다.  
- **확인 실패 시**: 오류 범위를 파악하고, **부모 요구사항 ID**를 기준으로 **bugfix 하위 요건** `docs/requirements/{부모ID}-bugfix-{N}.md` 를 생성해 수정한 뒤, **재시작·확인을 다시 수행**한다. **모든 확인이 통과할 때까지** 반복한다.  
- 상세: `docs/workflow/ERROR-FIX-WORKFLOW-FLOWCHART.md` § "검증 단계: 재시작·정상 실행 확인·bugfix 반복", `/verify` 커맨드.

1. **프론트엔드 검증**
   - [ ] API 전달 파라미터 확인
   - [ ] UI 동작 확인
   - [ ] 에러 처리 확인

2. **백엔드 검증**
   - [ ] API 파라미터 테스트 케이스 작성 및 실행
   - [ ] 로그 확인
   - [ ] 성능 확인 (해당 시)

3. **통합 테스트**
   - [ ] 전체 플로우 테스트
   - [ ] 엣지 케이스 테스트

### Step 5: 문제 발생 시 조치

#### 요건 반영 ✅, Side Effect ❌
1. 즉시 롤백
2. 영향도 분석 재수행
3. 개선된 코드 작성
4. 재검증

#### 요건 반영 ❌
1. 신규 코드 개선
2. 요건 재분석
3. 재검증

### Step 6: 문서화 및 완료

1. 요건 문서 업데이트
   - 테스트 결과 기록
   - 발견된 이슈 및 해결 방법 기록
   - 체크리스트 완료

2. **코드 커밋 (요구사항 해결 완료 시)**  
   검증 통과 및 §5·§6 반영 후, `.cursor/commands/commit-on-complete.md`에 따라 커밋한다. push는 사용자가 요청할 때만 수행.
   ```bash
   git add <변경된 경로>
   git commit -m "feat: 요건명 - 요건 설명"
   ```

3. 배포 준비 (해당 시)
