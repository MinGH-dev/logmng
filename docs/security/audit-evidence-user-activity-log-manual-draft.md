# 사용자 활동이력 로그 감사 증빙 자료 매뉴얼 (초안)

**문서 성격**: 보안·준법 담당자용 **운영·감사 준비 참고서** (요구사항 명세 아님)  
**대상 독자**: 보안담당자, 내부감사, 준법 인력  
**주제**: **사용자 활동이력 로그**를 감사 추적(audit trail)으로 삼을 때, **연산 유형별로 수집·제시할 증빙**을 정리한 초안  
**버전**: 초안 (Draft) — 조직 정책·배포 환경에 맞게 확정 필요

---

## 1. 목적

본 문서는 다음을 돕기 위해 작성한다.

- 감사·점검 시 **사용자 활동이력**(누가, 언제, 무엇을 했는지)과 함께 제출할 **증빙 자료의 종류**를 명확히 한다.
- 연산 유형(**삭제**, **변경**, **추가**)에 따라 **무엇이 “복원 가능하거나 기록되어야 하는지”**를 조직 기준으로 정렬한다.
- **행위 유형을 구분한 뒤** 기술적으로 **마스터+이력**으로 둘지 **이력(append 로그)만**으로 둘지 등 **기록 구조**를 선택할 때, **감사 증빙이 어느 출처에서 완결되는지**(통합 감사 로그만인지, 엔티티 버전 테이블·백업과 병행인지)를 정리한다. (내부 **아키텍처 검토** 요약 반영)
- 제품·환경별 세부사항은 **미확정 항목**으로 남기고, PO·운영과 함께 확정할 수 있게 한다.

---

## 2. 범위

### 2.1 포함

- **사용자 활동이력 로그**를 중심으로 한 감사 증빙 **자료 범주**(메타데이터, 스냅샷, 전·후 값 등).
- **행위 유형군**(인증, 조회·보내기, 변경 등)과 감사 시 **통상 중시하는 증빙 포인트**(참고 분류).
- **기록 구조**와 증빙의 관계: **마스터+이력**, **이력 전용(append 감사 로그)**, **하이브리드**, **이벤트 소싱** 수준의 비교 및 **증빙 담당자가 확인할 질문**(아키텍처 검토 요약).
- **삭제·변경·추가** 이벤트 유형별 **권장 증빙 매트릭스**.
- **인앱 복사(선택 텍스트) 기록·조회**: 브라우저 앱 내에서 사용자가 선택·복사한 텍스트를 활동이력(또는 동등 UI)에 남기고, 권한 있는 역할이 **감사·운영 목적**으로 조회할 수 있게 하는 경우의 **기술적 증빙 포인트**와 **보안·거버넌스** 주의사항(§4.5·§4.6).
- 증빙의 **보관·취급**에 대한 고수준 주의사항(비밀·키값·환경설정은 다루지 않음).

### 2.2 제외

- 애플리케이션 구현 상세, API 계약, DB 스키마 정의(본 저장소의 별도 계약·요구 문서 영역).
- 특정 법령·규제 조항에 대한 법률 해석(법무 검토 필요).
- 실제 운영 **비밀번호·토큰·개인 식별자**가 포함된 예시.

## 3. 용어 정의

| 용어 | 설명 |
|------|------|
| **사용자 활동이력 로그** | 시스템 내에서 사용자(또는 서비스 계정)의 행위를 시간 순으로 남긴 기록. 감사 시 “누가·언제·무엇을·어떤 유형으로” 했는지의 **기본 추적선**이 된다. |
| **감사 증빙** | 감사인·내부통제·규제 대응을 위해, 주장(“적절히 기록·통제되었다”)을 뒷받침하는 **원천 자료·부속 설명**의 묶음. |
| **연산 유형** | 본 매뉴얼에서 다루는 세 가지: **삭제(Delete)**, **변경(Update)**, **추가(Create/Insert)**. |
| **행위 유형군** | 기술·운영 설계에서 쓰는 넓은 분류(예: 인증·조회·보내기·뮤테이션·관리). 연산 유형(삭제/변경/추가)과 함께 **로그 페이로드·보존 정책**을 일관되게 묶을 때 사용한다. |
| **Append-only / 감사 적재** | 시간 순으로 **추가만** 하는 기록 방식. 감사 목적에서는 임의 변경·삭제가 어렵게 설계하는 경우가 많다. |
| **마스터+이력(엔티티)** | 업무 엔티티의 **현재 상태(마스터)**와 **버전·유효기간 등 이력 테이블**을 함께 두는 패턴. DB에서 **특정 시점의 값**을 조회해야 할 때 검토한다. |
| **하이브리드(기록 구조)** | 도메인 **CRUD 테이블**은 운영 마스터로 유지하고, **횡단 감사 로그**(단일 append 테이블 또는 동등 스트림)에 유형별 **페이로드**를 싣는 일반적인 조합. |
| **삭제 증빙** | 제거된 대상의 **내용 또는 식별 가능한 기록**이 사후에 **재구성되거나**(예: 소프트 삭제+스냅샷) **명시적으로 로그에 포착**된 자료. 단순 “삭제됨” 플래그만으로는 부족할 수 있다. |
| **변경 증빙** | 동일 객체에 대한 **변경 전(before)** 와 **변경 후(after)** 를 대응시킬 수 있는 기록. |
| **추가 증빙** | 신규 레코드 또는 신규 필드 값의 **실제 내용**(또는 허용 범위 내 요약)이 담긴 기록. |
| **PII** | 개인을 식별할 수 있는 정보. 증빙 수집 시 **최소 수집·마스킹·접근 통제** 원칙을 따른다. |

## 4. 행위 유형 분류와 기록 구조(마스터/이력) — 아키텍처 검토 반영

**배경**: 모든 사용자 행위를 로그로 남기려면 **행위 유형을 구분**한 뒤, 유형별 **데이터 구성**(예: 삭제 직전 스냅샷, 수정 전/후, 신규 값)을 정한다. 설계에서 **운영용 마스터 + 감사 이력**으로 둘지, **이력(append 로그)만**으로 충분한지에 따라 **감사인에게 제시하는 증빙의 출처**가 달라질 수 있다. 아래는 내부 **아키텍처 검토**를 요약해 증빙 매뉴얼에 반영한 것이며, **구현 명세나 API 계약은 아니다**.

### 4.1 행위 유형군(참고 분류)

| 유형군 | 예시 | 감사·증빙에서 통상 중시하는 점 |
|--------|------|--------------------------------|
| **인증·세션** | 로그인, 로그아웃, 인증 실패 | 누가·언제·성공 여부; 정책 허용 시 출처(IP, UA 등) — **비밀·토큰 본문은 로그에 넣지 않음** |
| **조회·접근** | 상세 보기, 목록, 검색(범위에 넣는 경우) | 리소스 유형, 필터(비식별화), **건수** 등; **전체 결과 본문**은 PII·용량 이슈로 **별도 정책** 검토 |
| **보내기** | CSV/Excel 다운로드 | 범위·건수·형식·**상관 ID**; **파일 내용**은 통상 로그 행에 넣지 않음 |
| **변경(뮤테이션)** | 생성, 수정, 삭제, 배정/해제 | 대상 식별 + 본 문서 **5장**의 삭제/변경/추가 증빙 요소 |
| **보안·관리** | 권한·역할·설정 변경 | 뮤테이션과 동등 이상의 **페이로드 통제·접근 통제** |
| **연동·배치** | 서비스 계정·배치 수행 | 수행 주체, 작업 ID, 요약 파라미터 |
| **클립보드·복사(인앱)** | 화면에서 텍스트 선택 후 복사, 그리드/상세 영역의 복사 단축키·버튼 | **복사 이벤트 시각·주체**, **소스 맥락**(화면·리소스 유형), **선택된 본문**(정책 허용 범위·상한); 앱 **외부** OS 클립보드와 구분해 증빙 범위를 정의 |

실제 제품에서는 **행위 코드(예: `action_type`) 표준 목록**과 **유형군별 허용 필드(화이트리스트)**를 별도로 확정한다.

### 4.2 마스터+이력 vs 이력 전용 vs 하이브리드 — 증빙 관점

| 구조 | 요지 | 감사·증빙에서의 의미 |
|------|------|----------------------|
| **이력 전용** | 행위마다 append로 한 건씩 적재; **현재 상태**는 별도 업무(OLTP) 테이블 | **기록 시점**에 삭제 스냅·before/after·신규 값을 **로그 페이로드**에 넣으면 증빙 확보 가능. “과거 시점 T의 **DB에 저장된 값**”을 **로그 재생·스캔 없이** 입증해야 하면 한계가 있을 수 있음. |
| **엔티티별 마스터+이력** | 운영 **현재 행** + **버전/유효기간 이력 테이블** | **특정 시점 필드 값** 조회·시점 비교를 제품이 DB 수준에서 보장할 때 유리. 마스터와 이력 **정합성**·보관 **이중 관리** 부담. |
| **하이브리드**(일반적 권장안) | 업무 **도메인 테이블**은 기존 CRUD **마스터**; **횡단 감사 로그**는 별도 append 스트림 | 감사는 **통합 피드**로 추적, 업무 데이터는 기존 구조 유지. 페이로드가 불완전하면 “이력만으로 완전 복원”은 제한될 수 있음 — **변경과 동일 트랜잭션 기록** 등은 기술 문서에서 정의. |
| **이벤트 소싱** | 상태를 이벤트 누적으로 복원 | 감사력은 강하나 **운영·구현 복잡도**가 큼; “활동이력 감사”만을 위한 **기본 선택**은 드묾. |

**증빙 담당자가 확인할 질문**

- 규제·내부 기준이 요구하는 것이 **“누가 무엇을 했는지와 그 순간의 맥락(스냅/전후)”** 인지, **“DB에 보관된 과거 시점의 값”** 자체의 입증인지.
- 전자에 가깝다면 **이력 전용(풍부한 페이로드)**로도 종종 충분하다. 후자가 필요하면 **해당 엔티티에 버전/시점 테이블** 등을 **추가** 검토한다.

### 4.3 조건부 선택(아키텍처 검토 요약)

- **이력 전용(단일 감사 테이블 등)**을 우선 검토할 때: 목적이 **보안·운영 감사**(행위와 맥락 입증)이고, **현재 상태**는 기존 업무 테이블에 두면 될 때. **삭제 스냅·before/after**는 **쓰기 시점**에 허용 목록 기준으로 페이로드에 담는다.
- **엔티티별 마스터+이력**을 추가할 때: **“시점 T의 필드 X 값”**을 로그만으로 답하기 어렵고, 제품이 **DB에서 시점 조회**를 보장해야 할 때.
- **하이브리드**: 위 둘을 **병행**하는 형태가 많다. **모든 엔티티**에 마스터+이력을 두기보다, **시점 입증이 필요한 도메인**에만 **선택적**으로 버전 저장을 두는 편이 일반적이다.

### 4.4 본 저장소 구현과의 정렬(참고)

내부 기술 검토에 따르면, 본 제품은 **`user_activity_log`에 append 형태로 감사 이벤트를 적재**하고, 유형별 상세는 **`action_detail` 등 JSON**으로 확장하는 패턴과 정합적이다. 감사 증빙 패키지를 구성할 때는 **증빙이 활동이력 단일 출처로 완결되는지**, **엔티티 버전 테이블·백업 스냅샷**을 **어떤 유형의 사건**에 함께 첨부하는지 표로 정리해 두는 것이 좋다.

### 4.5 인앱 복사(Clipboard) 행위의 기술적 증빙·조회

**구현·증빙 범위(명시)**: **권한 있는 역할**이 **활동이력**(또는 이와 **동등한 조회·감사 UI**)에서, 사용자가 **앱 내에서 복사한 텍스트**(선택 영역을 기준으로 수집·전송된 본문)를 **조회**할 수 있도록 하는 것은, 본 매뉴얼에서 다루는 **구현·감사 증빙 범위**에 포함된다. (앱 밖·OS 전역 클립보드 전체를 수집하는 것과는 구분한다.)

#### A. 경계 표(신뢰 경계)

| 구분 | 설명 |
|------|------|
| **클라이언트(브라우저)** | 선택·복사 이벤트는 브라우저에서 관측된다. **타 사이트·타 앱·OS 전역**에서의 복사는 본 기능의 관측 범위 밖일 수 있다. |
| **서버·저장소** | 감사 레코드는 서버가 수신한 뒤 append 스트림(예: `user_activity_log`)에 적재되는 패턴이 일반적이다. |
| **무결성 전제** | 클라이언트 전송 본문은 **변조 가능**하므로, 강한 무결성 요구 시 **서버 측 상관 ID·요청 메타**와 함께 **운영 절차·상호 검증**을 검토한다. |

#### B. 상관 필드(권장)

- 사용자·역할 식별(비밀·토큰 본문 제외)
- 일시(조직 표준 타임존·UTC 정책)
- 세션·요청·활동 건 **상관 ID**(제품 표준 필드명에 맞출 것)
- 화면·기능 코드, 리소스 유형·식별자(비민감·화이트리스트 범위)
- 복사 **발생 맥락**(예: 목록 그리드 셀, 상세 패널 구역명)

#### C. 페이로드(고수준)

- **선택·복사된 텍스트 본문**(최대 길이·잘림 정책)
- **행위 유형** 코드(예: 인앱 클립보드 복사)
- **길이·잘림(truncation) 표시** — 장문일 때 감사 해석이 가능하도록
- 비밀·토큰·전역 클립보드 덤프는 **담지 않음**(§4.6과 정합)

#### D. 색인·조회

- 시간대·사용자·행위 코드 등으로 **필터·검색**이 가능한 설계인지
- **권한 있는 역할**만 동일 UI에서 본문을 열람할 수 있는지(IAM·화면 권한과 일치)
- 민감 필드가 섞일 수 있으므로 **표시 마스킹·다운로드 제한**은 조직 정책·§4.6과 병행 확정

#### E. 알려진 제한

- 브라우저·엔터프라이즈 정책에 따라 **클립보드 API**가 제한될 수 있다.
- **앱 외부**에서 수행한 복사는 기록되지 않을 수 있다.
- 초장문 선택은 **상한 초과 시 잘림**만 남을 수 있다.
- 이벤트 빈도가 높으면 **저장·보관 비용**이 커질 수 있어 상한·운영 조정이 필요할 수 있다.

#### F. 체크리스트 보강(설계·감사 대응)

- [ ] 인앱 복사가 **활동이력 append**로 남는가?

- [ ] 페이로드가 **해당 화면 선택분**으로 한정되는가(비밀·토큰·무관한 클립보드 내용 배제)?

##### Implementation scope note (English)

For audit and evidence purposes, **implementation scope** includes enabling **authorized roles** to **query and review the text that was copied in-app**—via the **user activity history** feature or an **equivalent audit/operator UI**—subject to the same **retention and access controls** as other activity events. This **does not** extend to logging **system-wide** or **out-of-app** clipboard contents.

### 4.6 보안·거버넌스: 브라우저 내 복사(선택 텍스트) 기록·조회

앱 내에서 사용자가 **선택한 텍스트의 복사**를 활동이력에 남기고 조회할 수 있게 하는 경우, **PII·업무 비밀·남용** 리스크가 커질 수 있으므로 아래를 **조직 정책·법무 검토**와 함께 확정한다.

#### 범위 포함·제외

- **포함(전형)**: 제품 UI에서 **명시적 복사 동작**(단축키·메뉴·버튼) 또는 **정책으로 정의한 선택 기반 복사**와 연계되어 서버에 전달되는 **선택 영역 본문**.
- **제외(전형)**: **OS 전역 클립보드 전체** 스냅샷, **타 애플리케이션**에서의 복사, **비밀 입력 필드** 본문, 사용자가 **동의·고지 범위 밖**인 임의 텍스트 수집.

#### PII·비밀·최소화

- 복사 본문에는 **이름·연락처·식별자** 등 PII가 **섞일 수 있음**을 전제로 **수집 최소화·길이 상한·필드 제외 목록**을 둔다.
- **비밀번호·세션 토큰·API 키·카드번호** 등은 로그에 **넣지 않는다**. 화면 설계상 위험 구역은 **복사 이벤트 자체를 기록하지 않거나** 본문을 **적재하지 않는** 방식을 검토한다.

#### 투명성·거버넌스

- 내부 **개인정보 처리방침·내부 고지**에 “선택·복사 기록”이 포함되는지 **준법·법무**와 정합성을 확인한다.
- 기능 **ON/OFF**, **본문 상한**, **역할 매핑** 변경은 **변경 관리·승인** 절차에 둔다.

#### 접근 통제

- 복사 본문 조회는 **업무 필요 최소 역할**에 한정한다.
- **누가 본문을 조회했는지**는 가능하면 **별도 접근 감사**(또는 동등한 흔적)로 남긴다(내부 위협 대응과 §7 항목과 연계).

#### 보존·삭제

- 다른 활동이력과 **동일 보존 기간·법적 보류(legal hold)·안전 폐기** 원칙을 적용한다.
- 만료·삭제 시 **복구 불가** 절차를 조직 표준에 맞게 문서화한다.

#### 하지 말아야 할 것

- 감사 목적을 넘어 **과도한 전역 감시**로 확장하는 것.
- **암호화되지 않은 채널**로 민감 본문을 전송·보관하는 것(전송·저장 암호화는 제품·인프라 표준에 따름).
- **목적 외** 열람·보내기·재가공.

#### 구현·운영용 보안 수용 기준(참고)

- **S-1 (범위 명확화)**: 기록 대상을 **인앱 선택·복사**로 정의하고, OS·타 앱 클립보드는 **기본 제외**로 문서화한다.
- **S-2 (금지 데이터)**: 비밀·토큰·키·결제 민감정보 등 **금지 필드**는 페이로드에 포함하지 않는다.
- **S-3 (PII 통제)**: PII 혼재 가능 시 **마스킹·조회 권한·목적 제한**을 내부 정책에 둔다.
- **S-4 (최소 권한)**: 본문 조회 권한은 **역할 기반**으로 제한하고, **권한 부여·회수**를 주기적으로 점검한다.
- **S-5 (투명성)**: 이용자·임직원 고지 범위와 **실제 수집**이 일치하는지 **법무·준법**과 확인한다.
- **S-6 (보존·삭제)**: 보존·파기는 **활동이력 전반 정책**과 동일 선상에서 관리한다.
- **S-7 (변경 통제)**: 수집 강도·필드·상한 변경은 **승인된 변경**만 반영한다.

**법무 관련 안내**: 위 항목은 **기술·운영 체크리스트**이며, **적법성·고지·동의 필요성** 등에 대한 **최종 판단은 법무** 검토에 따른다.

## 5. 연산 유형별 증빙 매트릭스

아래는 **조직이 감사 시 증빙 패키지를 구성할 때** 참고할 수 있는 **권장 자료 목록**이다.  
실제 시스템이 모든 항목을 자동으로 남기지 않을 수 있으므로, **기록 공백**은 “미확정·개선 과제”로 관리한다.

### 5.1 삭제 (Delete)

| 증빙 요소 | 설명 | 비고 |
|-----------|------|------|
| **삭제 대상 식별자** | 삭제된 엔티티의 내부 식별자·업무 키(비민감 범위) | 외부 감사 시 내부 ID 공개 범위는 정책에 따름 |
| **삭제 시점·주체** | 일시, 수행 계정(또는 역할), 세션·출처 IP 등 정책 허용 범위 | IP 등은 PII·보관기간 정책 준수 |
| **삭제 직전 스냅샷** | 삭제 전 **전체 레코드** 또는 규정이 요구하는 **필수 필드**의 값 | 물리 삭제만 하는 경우 사후 복원 불가 → **사전 스냅샷·보관 연계** 필요 여부 검토 |
| **삭제 사유·승인** | (해당 시) 티켓·승인 ID, 근거 | 내부통제 절차와 연계 |

**요지**: 감사 관점에서 “무엇이 사라졌는지”가 **문맥과 함께 재구성**되거나 **명시적으로 기록**되어야 한다.

---

### 5.2 변경 (Update)

| 증빙 요소 | 설명 | 비고 |
|-----------|------|------|
| **변경 대상 식별자** | 수정된 객체의 식별 정보 | |
| **변경 전(before)** | 수정 직전의 해당 필드(또는 행) 값 | 필드 단위 변경이면 **필드별 before** 권장 |
| **변경 후(after)** | 수정 반영 후 값 | |
| **변경 시점·주체** | 일시, 수행 계정 | |
| **변경 집합의 대응** | 동일 트랜잭션·요청에서 여러 필드가 바뀐 경우 **한 묶음**으로 추적 가능 | 로그 설계 시 correlation id 등 검토 |

**요지**: “무엇이 어떻게 바뀌었는지”를 **before/after 대응**으로 증명할 수 있어야 한다.

### 5.3 추가 (Create / Insert)

| 증빙 요소 | 설명 | 비고 |
|-----------|------|------|
| **신규 대상 식별자** | 생성 후 부여된 식별자 | |
| **추가된 내용** | 신규 행의 **주요 필드 값** 또는 규정상 필요한 속성 | 민감 필드는 마스킹·별도 보호 저장소 원칙 |
| **생성 시점·주체** | 일시, 수행 계정 | |
| **초기 상태의 무결성** | (해당 시) 템플릿·기본값 적용 여부를 설명할 수 있는 자료 | |

**요지**: “새로 무엇이 생겼는지”가 **구체 값**과 함께 활동이력 또는 연계 저장소에 남는지 확인한다.

## 6. 보관·취급 (고수준)

다음은 **원칙** 수준이며, 기간·시스템·역할은 조직 표준과 제품 배포 환경에 맞게 확정한다.

- **접근 통제**: 활동이력·증빙 저장소는 **업무 필요 최소 인원**에게만 부여하고, 조회·다운로드를 **별도 로깅**하는 것이 바람직하다.
- **무결성**: 감사 목적 기록은 **임의 수정·삭제**가 어려운 저장 방식(WORM, append-only, DB 권한 분리 등)을 검토한다.
- **보관 기간**: 법·내부 규정·계약에 따른 **최소 보관기간**을 정하고, 만료 시 **안전 폐기** 절차를 둔다.
- **PII**: 예시·샘플·첨부 자료에는 **실명·실번호·실제 접속식별자**를 넣지 않는다. 필드명은 일반명(예: `user_display_name`, `internal_ref_id`) 수준으로 기술한다.
- **교차 출처**: 한 이벤트가 **여러 시스템**(앱 DB, 메시지 큐, 외부 IdP)에 흔적을 남길 수 있으면, 감사 시 **상호 참조 가능한 상관 키**를 문서화한다.
- **기록 구조와 보관**: **이력 전용**이면 감사 로그(및 아카이브) 보관 정책이 증빙의 중심이 된다. **엔티티 버전 테이블**을 쓰면 **마스터·이력·백업** 간 보관·법적 보류(legal hold) 범위를 **일치**시키는지 점검한다.

**본 문서는 비밀키·환경 변수·네트워크 도면 등 운영 기밀을 다루지 않는다.**

## 7. 감사 준비 체크리스트 (보안담당자용)

감사 전에 다음을 **즉답 가능한지** 점검한다. “아니오”이면 증빙 공백·개선 이슈로 기록한다.

1. **범위**: 사용자 활동이력이 **어떤 화면·API·배치**까지 커버하는가? (미기록 영역 목록)
2. **삭제**: 물리 삭제 건에 대해 **삭제 직전 데이터**를 다른 매체에 보존하는가, 아니면 로그에 **전부 또는 요약**이 남는가?
3. **변경**: 모든 민감 필드에 대해 **before/after**가 남는가, 일부만 남는가? (남지 않는 필드 목록)
4. **추가**: 신규 생성 시 **초기 속성 값**이 활동이력에 포함되는가, DB 스냅샷으로만 입증 가능한가?
5. **시간**: 모든 기록이 **동기화된 시각 기준(UTC/KST 등)** 을 사용하는가?
6. **주체**: 공용 계정·자동화 계정의 행위가 **실사용자와 구분**되는가?
7. **조회 추적**: 관리자가 활동이력·원본 데이터를 대량 조회·보낸 사실이 **별도 기록**되는가? (내부 위협·유출 대응)
8. **보관·삭제**: 로그·백업의 **보관 정책과 실제 설정**이 일치하는가? (법무·DBA와 확인)
9. **샘플 패키지**: 최근 **삭제·변경·추가** 사례 각 1건 이상에 대해, **감사인에게 제출 가능한 형태**로 묶음을 만들 수 있는가?
10. **기록 구조·출처**: 증빙이 **통합 활동이력(append 로그)만**으로 완결되는가, **엔티티 버전 테이블·백업**을 어떤 유형에 병행하는가? (4장과 표로 문서화했는가?)
11. **인앱 복사**: 복사 본문이 **활동이력(또는 동등 UI)**에 남고, **권한자만** 조회 가능한가? 페이로드에 **금지 데이터**가 섞이지 않도록 화면·상한·화이트리스트가 정의되어 있는가? (§4.5·§4.6)

## 8. 미확정 사항·면책

본 초안은 **제품·배포 환경·내부 규정**에 따라 달라질 수 있다. 아래는 **제품 오너(PO)·운영·법무**와 확정이 필요한 대표 항목이다.

- 본 시스템의 **사용자 활동이력**이 위 세 연산 유형을 **모두 동일한 깊이로** 기록하는지 여부.
- **삭제**가 물리삭제인지 소프트삭제인지, 그리고 **감사 요구 수준**에 맞는 **스냅샷·보관소** 존재 여부.
- **변경** 로그에 **민감 필드**를 그대로 넣을지, **해시·마스킹·별도 암호화 저장**할지에 대한 조직 정책.
- 증빙 수집 시 **개인정보 처리방침·동의** 및 **제3자 감사** 시 데이터 반출 범위.
- 장기 보관 시 **비용·암호화 키 로테이션** 등 운영 한계.
- **시점 DB 입증**이 필요한 엔티티 목록과, 그에 대한 **버전/이력 테이블** 또는 동등 수단의 유무(4장과 연계).

**면책**: 본 문서는 법률 자문이 아니며, **최종 증빙 적격성**은 감사 기준·계약·적용 법령에 따른다. 구현 세부는 별도 기술 문서·계약과 대조해야 한다.
